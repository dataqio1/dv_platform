Cross-Engine Data Compare — how the algorithm works

Comparing a table in Oracle against the “same” table in Snowflake without moving the data. The trick: hash each row inside each database with a standard digest (Oracle STANDARD_HASH = Snowflake SHA2), then only move tiny per-bucket summaries across the wire — and prune everything that already matches. An adaptive gate decides, cheaply, when hashing stops paying off and bails to a straight streaming pull.

1

Canonical row hash the foundation

Each side builds the same text for a row — numbers as stripped decimals, dates as YYYY-MM-DD, nulls folded — then SHA-256s it. Equal rows ⇒ identical hash on both engines. (Without this, 1.5 vs 1.5E+000 would make every row look different.)

rowhash = SHA256( id |'|'| name |'|'| strip(amount) |'|'| to_char(dt,'YYYY-MM-DD') |'|'| … )
2

Chunked first pass prune + gate + progress, in one loop

Break the key range into chunks of ≈100k rows (a small table = 1 chunk). Walk them in order; each chunk is one (COUNT, Σ rowhash) per side. A chunk that matches is pruned — never read again; a chunk that differs is queued. This replaces the old single whole-table scan — bounded per query, emits progress per chunk, and all chunks matching ⇒ identical, 0 rows moved.

for each ~100k-row chunk: (COUNT, Σ rowhash) per side → match ⇒ prune · differ ⇒ queue
3

Running dirty-chunk % the cheap decision

The fraction of chunks that differ is the gate — no separate scan. It only grows, so once it clears the threshold the final value can’t drop below it → decide immediately (early bail). Scattered diffs dirty every chunk; a contiguous block dirties a few.

dirty_chunks / total → compare against bail threshold (default 60%)
4

Branch on dirty-bucket %

A bucket is “dirty” if its count or checksum differs. How many are dirty tells you whether pruning can still save work:

prune
few dirty

Most buckets match → skip them entirely. Recurse only into dirty buckets, bisecting down to small leaves.

drill
dirty ≤ 60%

Dirty regions are localized → descend them, pull only the divergent leaves, and cell-compare those rows authoritatively.

bail
dirty > 60%

Almost every bucket differs → hashing can’t prune anything. Stop and hand off to the streaming engine (pull once), instead of a query storm.

5

Leaf compare authoritative

Only divergent leaf ranges (a few hundred rows each) are pulled from both sides and compared cell-by-cell by the in-memory engine — the judge. So a hash coincidence can only ever cost an extra leaf pull, never a wrong verdict. Matched buckets were proven equal by checksum and are never read.

The one idea to remember: what kills a hash compare is not the diff percentage — it’s the diff dispersion. A bucket is all-or-nothing: one changed row dirties the whole bucket. Scatter just 1% of changes across the key space and every chunk goes dirty, so hashing must re-read the whole table — worse than a plain pull. The chunked first pass measures exactly this as it scans and decides: prune pull dirty chunk or bail.

Engine: fingerprint_compare (cross-engine bisection) · gate threshold fingerprint_bail_pct (default 0.6) · leaf judge compare_rows. Same-database pairs use the pushdown recursive_hash/snowflake_hash variants; small tables load in-memory directly.

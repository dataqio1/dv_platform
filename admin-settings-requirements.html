Admin & Settings — Requirements

A single, RBAC-gated home for everything an administrator does — members & roles, connections, audit, outbound integrations (email · Slack · Teams · Jira · Rally), secrets, scheduler and system config. Grounded in the platform as it exists today; each capability is tagged by how much already exists. For review & sign-off before implementation.

1Goals & guiding principles

Consolidate admin functionality that is today scattered (connections, projects, tags), invisible (audit, scheduler), or missing (members, integrations) into one place — without re-inventing the tenancy and permission model that already exists.

  • One home for governance — members/roles, connections, audit, integrations, secrets, system config.
  • RBAC-gated, least privilege — the tab and each section render only for the matching permission.
  • Mode-aware — adapts across local / server / prod and identity via local / OIDC / LDAP.
  • Everything audited — reuse the existing AuditLog + audit.record(); no silent mutations.
  • Reuse the tenancy model — Organization → Group → User via Membership(role); 5 roles, 7 permissions.
  • Secrets never leave the server — credentials stay in the SecretStore, consistent with connections today.

2Placement & access control

A new top-nav Admin tab (after Connections), visible only when the user holds an admin permission. A left rail inside Admin lists the modules; each module is independently gated, so the same tab shows more or less depending on the role.

ConcernRule
Tab visibilityRendered only if can("manage_group") or can("manage_connections") — the frontend already exposes can(permission) from /me.
Section gatingEach module checks its own permission (below). An editor sees nothing; group_admin sees most; org_admin sees org-level extras.
EnforcementBoth ends: backend ctx.require(Permission.X) on every endpoint and frontend can(...) on every section.
Mode signalA lightweight GET /system/info tells the UI the runtime mode & identity provider so it can hide/disable what doesn't apply (e.g. editing roles under LDAP).

Unified design

ElementDesign
EntityOne Integration = {id, category: channel|ticketing, provider, name, enabled, config(JSON), secret_ref, status, last_delivery_at}.
ExtensibilityProvider registry: channels implement send(); ticketing implements create_issue() / sync_status(). Adding a provider = one registry entry. Extends today's Notifier (report-only) into multi-channel + a new TicketingProvider protocol.
Test/integrations/{id}:test — send a test message / create-and-close a test ticket.
Routing rulesevent → integration(s) → field mapping. Events: incident opened · severity ≥ threshold · monitor run failed · report generated. Dedup/throttle by incident fingerprint so a flapping check doesn't spam or open 50 tickets.
Two triggersIncident alerting (today incidents notify no one) and report delivery (unifies today's email/slack-in-delivery-JSON under managed channels).
Audit & errorsEvery create/edit/test/route-change audited; each delivery/ticket attempt logs success/failure with the error surfaced (no silent swallowing).

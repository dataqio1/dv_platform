Historical Baseline DQ Rules — Implementation Plan

Validate any numeric value against its own history — not just fixed thresholds. A value (from SQL, a file, or later a BI dashboard) is captured every run, stored as history, and compared to a baseline (avg / median / stddev band / previous value / min–max). Surfaces in both Data Observability and Data Validation.

Key finding: ~60% of this already exists in the platform. The Metric table is the observation store, the DQ rule engine already captures scalar values via SQL, anomaly.py already computes a statistical baseline (median+MAD band, calendar-aligned, Learning on thin history), and the integrations we just shipped cover the alerting FRs. The real new work is a baseline rule family + first-class metric definitions + the enriched observation/lifecycle, not a greenfield build.

2Proposed architecture

One Metric = a named numeric value + a source. Each run writes one Observation to history. Baseline rules compare the new observation to a baseline computed from valid history. A metric can be attached to a monitor (observability) or a project/compare (validation), or stand alone — so it shows up in both surfaces with identical logic.

Metric (source: SQL/file/dashboard)→ capture value→ Observation (history)→ baseline from valid history→ rules evaluate→ status + alert

Statuses carried on every result:

PassWarn FailLearningError

The capture engine (SQL/file/dashboard) and the baseline evaluator are pure and source-agnostic — all three sources produce the same observation record, so rules work identically (as the spec requires).

3The baseline rule family

Six rule types, each Warn or Fail, one- or two-sided. All operate on the metric's own history window.

Baseline windows (FR-B1): last N observations, last N days, or calendar-aligned (same weekday ×N weeks / same date last year — already in anomaly.py). Baselines exclude Excluded/Error/unaccepted-Fail points. Cold start → Learning until ≥ min history (default 5), with an optional static fallback threshold.

5Run flow (reuses the existing worker + scheduler)

  1. Capture the value — SQL via the connector (reuse), file via FileConnector+extraction, dashboard (P2).
  2. Store one Observation (dedup by run_id). A capture/parse failure → Error, not Fail (FR-S6).
  3. Baseline per rule from valid history (exclude Excluded/Error/unaccepted-Fail).
  4. Evaluate each rule → Pass/Warn/Fail/Learning. Metric result = worst across its rules (FR-R1).
  5. Store result + alert via the integrations/routing already built; plain-language message (FR-E2).

Scheduled runs use the scheduler; ad-hoc/CI runs use dvp worker (exit codes for pass/fail come free). Everything stays in the customer's environment — zero egress (NFR-1), credentials from the connection store (NFR-2).

7Open questions — my recommendations

Fail values in the baseline?

FR-B2 says keep Fail values out until accepted.

Recommend: keep out by default (matches FR-B2) — prevents a bad spike from poisoning the band; user "Accept" pulls it in.

Default minimum history?

5 observations, or per-rule-type?

Recommend: default 5, overridable per rule; statistical needs more (≥ ~8–10) — anomaly.py already guards thin history.

Dashboard capture mechanism?

Browser extension only, or native Power BI / Tableau APIs?

Recommend: Phase 2; start with a generic selector + screenshot path, add native APIs later. (You flagged dashboard testing is new.)

Dimension cap per metric?

Limit (e.g. 500) to keep runs fast (NFR-4: 1k metrics/run).

Recommend: soft cap 500/metric with a surfaced warning (no silent truncation), configurable.
